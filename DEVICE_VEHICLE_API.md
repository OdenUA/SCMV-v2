# API: создание, редактирование, привязка и удаление устройств/транспорта

> Документ написан по результатам реверс-инжиниринга SCMV v1 (https://scmv.vpngps.com) через CDP-перехват WebSocket-трафика и контролируемые эксперименты на живом сервере (2026-09-10). Нужен для реализации функционала в SCMV v2.

---

## 1. Общий протокол

- Транспорт: **WebSocket** `wss://scmv.vpngps.com:4445/` (Origin должен быть `https://scmv.vpngps.com`, иначе 502).
- Формат пакетов: JSON.
- **Каждый** пакет (кроме login) содержит авторизацию открытым текстом:

```json
{"usr":"...","pwd":"...","uid":360,"lang":"en"}
```

- `uid` выдаётся сервером в ответе на `login` (`{"name":"login","type":"login","mid":0,"act":"init","usr":"...","pwd":"...","uid":0,"lang":"en"}`).
- `mid` — id модуля (счётчик в рамках клиента), не глобальный sequence.
- Сервер в ответе **эхом возвращает весь запрос**, добавляет служебные поля `dstport/dstaddr/srvport/srvaddr` и результат в `res`.
- Статус: `ern:0, msg:"ok"` — успех; ненулевой `ern` — ошибка.

### Структура модуля таблицы (`type:"etbl"`)

| act | Назначение | Вход | Ответ |
|-----|-----------|------|-------|
| `init` | Описание колонок | — | `res[0].cols` — массив описаний колонок |
| `setup` | Данные таблицы | `{filter:[], nowait:true, waitfor:[]}` | `res[0].f` — массив строк |
| `rowadd` | Создать пустую строку | — | `res[0].f[0]` — новая строка с присвоенным `id` |
| `rowsave` | Сохранить изменения | `{cols:{id, ...}}` | `res[0]` без данных (`ern:0`) |
| `rowdel` | Удалить строку | `{cols:{id}}` | `res[0].f=[{t:1, v:"<id>"}]` |
| `filter` | Фильтрация | `{filter:[{selecteddeviceid:["1929"]}]}` | отфильтрованные строки |

### Типы колонок (`cols[].t`)

| t | Значение |
|---|----------|
| 1 | id-поле (не редактируется, ключ строки) |
| 2 | **readonly**-поле — отображается, но клиент v1 не отправляет в `rowsave` |
| 3 | редактируемое поле (input или select, если есть `k` — список опций `[{val,key}]`) |
| 40 | флаг `editablemode` (d="yes") |
| 43 | флаг наличия кнопки добавления строки |
| 44 | флаг `nowaitfilter` |
| 47/48 | флаги показа header/footer |
| 49 | CSS-класс модуля |

**Важно:** в клиенте v1 при сохранении (`modul-etbl-src.js`, `defonrowsave`) отправляются только поля типов 3/4/5, у которых значение изменилось. Поля `t:1` и `t:2` никогда не отправляются. Одинарные кавычки в значениях экранируются как `''''`.

## 2. Задействованные модули

| Модуль (name) | Назначение | Десктоп |
|---------------|-----------|---------|
| `Device Edit` | Таблица устройств (создание/редактирование/удаление) | «Device» (did 59), «Device Edit» (did 74) |
| `Vehicle Edit Distribution` | Таблица транспорта (создание/редактирование/удаление) | did 103 |
| `Vehicle Show` | Readonly-представление: транспорт + join устройства | «Vehicle» (did 68) |
| `Device Track` / `Device Log` / `Device Alarm` | Данные устройства, фильтруются по `selecteddeviceid` | «Device» (did 59) |

Список десктопов пользователя: `{"name":"desktop","type":"desktop","mid":1,"act":"init",...}` → `res[0].desktops`.
Состав десктопа: `{"name":"desktop","type":"desktop","mid":1,"act":"setup","did":103,...}` → `res[0].modules`.

### Колонки `Device Edit`

`id` (t:1), `imei`, `workstatus`, `debug`, `proto`, `maxinactive`, `periodicaltime`, `betweentimeout`, `iccid`, `phone` — редактируемые; `sdate` — проставляется сервером при создании, клиент не отправляет.

### Колонки `Vehicle Edit Distribution`

| Поле | Тип | Комментарий |
|------|-----|-------------|
| `id` | t:1/t:2 | ключ строки |
| `number` | t:3 | госномер/название (в тестах туда писали IMEI — это просто текст) |
| `brand` | t:3 + 29 опций | марка (select) |
| `model` | t:3 | модель |
| `link` | t:3 + 3 опции | тип привязки (0 = обычная) |
| `notes` | t:3 | примечание |
| `fleet` | t:3 + 92 опции | парк/клиент (select) |
| `deviceid` | **t:2 (readonly!)** | **привязка к устройству — колонка «dev / imei»** |

### Колонки `Vehicle Show` (всё readonly, join-вью)

`№`, `id`, `number`, `brand`, `model`, `proto`, `fleet`, `v.id`, `imei`, `deviceid` (d.id), `iccid`, `devid`, `phone`. Удобен для проверки результата привязки.

## 3. Создание устройства

**Шаг 1 — создать пустую строку:**

```json
→ {"name":"Device Edit","type":"etbl","mid":2,"act":"rowadd","usr":"...","pwd":"...","uid":360,"lang":"en"}
← res[0].f[0] = {"id":1930,"imei":null,"workstatus":null,"debug":null,"proto":null,
                 "maxinactive":null,"periodicaltime":null,"betweentimeout":null,
                 "iccid":null,"phone":null,"sdate":"2026-09-10T19:16:30.076659"}
```

`id` присваивает сервер; `sdate` — автоматически.

**Шаг 2 — заполнить поля:**

```json
→ {"name":"Device Edit","type":"etbl","mid":2,"act":"rowsave",
   "cols":{"id":"1930","imei":"354002395180464","workstatus":"1","debug":"1","proto":"11",
           "maxinactive":"3600","periodicaltime":"10","betweentimeout":"5",
           "iccid":"8938003993053237166","phone":"674600764"}, ...}
← {"ern":0,"msg":"ok"}
```

Все значения — строки. Допустимо частичное обновление: слать `id` + только изменённые поля.

**Побочный эффект в v1 UI:** после создания клиент шлёт `act:"filter"` к `Device Track`/`Device Log`/`Device Alarm` с `filter:[{selecteddeviceid:["<id>"]}]`, затем с пустым массивом, затем снова с id — переключение фильтров таблиц на новое устройство. Для v2 это необязательно.

## 4. Создание транспорта

Перед работой модуль инициализируется: `init` (колонки + списки опций) → `setup` (все строки, ~187 КБ).

**Шаг 1 — rowadd:**

```json
→ {"name":"Vehicle Edit Distribution","type":"etbl","mid":2,"act":"rowadd",...}
← res[0].f[0] = {"id":1930,"number":null,"brand":null,"model":null,
                 "link":null,"notes":null,"fleet":null,"deviceid":null}
```

**Особенность (проверено экспериментально):** `rowadd` транспорта **подхватывает id последнего устройства, у которого ещё нет строки транспорта**. Если создать устройство (id 1930) и сразу сделать `rowadd` транспорта — вернётся тот же id 1930. Создание устройства **не** создаёт транспорт автоматически.

**Вторая особенность:** строка, возвращённая `rowadd`, **не сохраняется на сервере**, пока не выполнен `rowsave` (проверено: после `rowadd` без `rowsave` строка в `setup` отсутствует).

**Шаг 2 — rowsave:**

```json
→ {"name":"Vehicle Edit Distribution","type":"etbl","mid":2,"act":"rowsave",
   "cols":{"id":"1930","number":"TEST-1930","brand":"1","model":"130","link":"0",
           "notes":"примечание","fleet":"25"}, ...}
← {"ern":0,"msg":"ok"}
```

## 5. Привязка транспорта к устройству (`deviceid`)

Колонка **«dev / imei»** = поле `deviceid`. В v1 она **readonly (t:2)** во всех модулях, клиент v1 её никогда не отправляет (строки `deviceid` нет в JS-клиенте). Поэтому при создании пары через v1 UI привязка остаётся `null` и колонка пуста. У всех legacy-строк `deviceid == id` (самосвязь) — видимо, проставлялась через БД/админку.

**Ключевой факт (проверено):** сервер **принимает** `deviceid` в `rowsave`, хотя v1-клиент его не шлёт:

```json
→ {"name":"Vehicle Edit Distribution","type":"etbl","mid":2,"act":"rowsave",
   "cols":{"id":"1929","deviceid":"1929"}, ...}
← {"ern":0,"msg":"ok"}
→ проверка setup: {"id":1929, ..., "deviceid":1929}
```

### Рекомендуемый поток для v2 (создание пары с автопривязкой)

```
1. Device Edit / rowadd                    → получить id N
2. Device Edit / rowsave                   → cols:{id:N, imei, workstatus, debug, proto,
                                             maxinactive, periodicaltime, betweentimeout,
                                             iccid, phone}
3. Vehicle Edit Distribution / rowadd      → вернёт id (обычно тот же N — проверять!)
4. Vehicle Edit Distribution / rowsave     → cols:{id:<vehicleId>, number, brand, model,
                                             link, notes, fleet,
                                             deviceid: <id устройства из шага 1>}
```

- Если на шаге 3 сервер вернул другой id (устройство создано давно, «подхватывать» нечего) — в `id` подставить id строки транспорта, а в `deviceid` — id устройства.
- Привязку можно установить/изменить в любой момент отдельным `rowsave` с `cols:{id, deviceid}`.

## 6. Редактирование

Одинаково для обоих модулей: `rowsave` с `cols:{id:"<id>", <только изменённые поля>}`. Сервер делает частичное обновление — непереданные поля не трогаются. Ответ — `{"ern":0,"msg":"ok"}` без данных.

Пример (только смена примечания):

```json
→ {"name":"Vehicle Edit Distribution","type":"etbl","mid":2,"act":"rowsave",
   "cols":{"id":"1929","notes":"новое примечание"}, ...}
```

## 7. Удаление

```json
→ {"name":"Vehicle Edit Distribution","type":"etbl","mid":2,"act":"rowdel","cols":{"id":"1930"},...}
← res[0].f = [{"t":1,"v":"1930"}], ern:0
→ {"name":"Device Edit","type":"etbl","mid":2,"act":"rowdel","cols":{"id":"1930"},...}
← res[0].f = [{"t":1,"v":"1930"}], ern:0
```

**Порядок:** сначала транспорт, потом устройство. Проверено на паре 1930: обе строки удаляются независимо, каскада нет — если удалить только устройство, строка транспорта останется (и наоборот).

## 8. Подводные камни (чек-лист для v2)

1. `deviceid` readonly в v1 UI, но сервер его принимает в `rowsave` — **это и есть механизм привязки для v2**.
2. `Vehicle rowadd` подхватывает id последнего «свободного» устройства — всегда сверять возвращённый id.
3. `Vehicle rowadd` без последующего `rowsave` не создаёт строку на сервере.
4. Создание устройства не создаёт транспорт — оба `rowadd`+`rowsave` нужно делать явно.
5. Все значения в `cols` — строки.
6. Каждый пакет несёт `usr/pwd/uid/lang`.
7. Ответ сервера — эхо запроса + `res`; сопоставлять запрос/ответ удобно по `name`+`act` (поле `mid` одинаково в рамках модуля).
8. Каскадного удаления нет — удалять обе записи явно.
9. Экранирование кавычек в v1: `'` → `''''` (стоит проверить, требуется ли это сервером, или это особенность клиента).
10. Поле `number` у транспорта — свободный текст, на привязку не влияет (IMEI туда писать бессмысленно для связки).
